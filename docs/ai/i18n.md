# i18n Reference — EN/DE Translation System

TOC: Concept · Build-time artifacts · Runtime lookup · UI strings ·
Bilingual search · Routing/SEO · Adding things · Terminology · Remainders

## 1. Concept in one paragraph

The entire data model is English (slugs, ids, keys, hashes, DB rows).
German exists as (a) committed build-time name artifacts for entities and
(b) i18next UI-string resources. The active language is decided by the URL
(`/:lang`), synced into i18next, and applied only at the render edge.
Nothing German ever flows back into models, links, or storage.

## 2. Build-time German artifacts

- Generator: `scripts/build-i18n-data.mjs` (`npm run i18n:data`) — fetches
  `language.name === 'de'` entries from PokéAPI with concurrency ~8 and
  retry on 429/5xx. Commit its output; do NOT fetch German names at
  runtime (the grid needs 1025 names at once).
- Output (`src/data/i18n/de/`): `pokemon.json` (`id → {name, genus}`),
  `moves.json`, `abilities.json`, `items.json`, `types.json`,
  `locations.json`, `regions.json` — each `slug → German name` —
  plus `search-index.json` (lowercased German name → slug/id).
- Regenerate only when new Pokémon/moves/items ship or coverage gaps are
  found. The JSONs are committed, so CI/devs need no network.

## 3. Runtime lookup layer

`src/lib/i18n-data.ts` exports `nameOfPokemon(id|slug)`,
`genusOfPokemon(id)`, `nameOfMove/Ability/Item/Type/Location/Region(slug)`
(+ method/eggGroup/growth/nature/pocket helpers). Resolution: active
language → de artifact → English fallback (pretty-printed slug).
Reactivity: components must subscribe via `useTranslation()` /
`useLanguage()` so they re-render on language switch.
Rule: anywhere an entity name hits the screen, go through this layer.
Raw `pokemon.name` / `move.name` in JSX is a defect.

## 4. UI strings

- Resources: `src/i18n/locales/{en,de}/translation.json`, one namespace,
  nested keys by area (`nav.*`, `detail.moves.*`, `maps.commandBar.*`, …).
- Parity is enforced by convention and review: every key exists in both
  files. Missing keys = bug; i18next must never emit missing-key warnings.
- Detector: `order: ['path', 'localStorage', 'navigator']`,
  `lookupFromPathIndex: 0`, storage key `pdx2.lang`,
  `fallbackLng: 'en'`.
- Number/unit formats are locale-aware: German uses decimal comma and
  dot thousands separator (`Intl.NumberFormat('de-DE')`), heights/weights
  like „0,7 m / 6,9 kg".

## 5. Bilingual search

All search surfaces (global SearchCommand, grid filter, Versus/TeamBuilder/
Nuzlocke autocompletes) accept both languages: German input resolves via
`search-index.json` to the English slug, then matches the English index;
display follows the active language. Keep fuse.js indexes fed with German
aliases when you add a new search surface.

## 6. Routing & SEO

- Every route under `/:lang`; internal links only via `LocaleLink` /
  `useLocalePath()` (see `references/architecture.md` §4 for the redirect
  matrix and LangGate sync).
- `SeoHead`: per-route hreflang `de`/`en`/`x-default`, canonical,
  localized `document.title`. Extend its title map when adding pages.
- The Navbar `DE | EN` segment control navigates to the same path with
  the other prefix, preserving query/hash.

## 7. How to …

**Add a UI string:** add key to BOTH locale files (German first-class,
not an afterthought), use `t('area.key')` in the component.

**Localize a new entity kind:** extend `scripts/build-i18n-data.mjs`,
run it, commit the artifact, add a `nameOfX` helper in `i18n-data.ts`,
use it at the render edge.

**Add a page:** route inside the `/:lang` tree, links via `LocaleLink`,
title key for `SeoHead`, all strings in both locales, smoke-test both
language URLs.

## 8. German terminology (established choices)

Attacken (moves), Fähigkeit (ability), Wesen (nature), Typen,
Fangrate (catch rate), Basis-EP (base EXP), Ei-Gruppen (egg groups),
Gattung (genus), Wachstum (growth rate), Ruf (cry), Sprite-Museum,
Karten (maps), Flucht/front/back shiny per official games. Kanto city
names per official German games (Alabastia, Vertania City, Mauzi City…).
Style: short substantive labels, no du-form, no anglicisms where an
official term exists.

## 9. Known English-only remainders (accepted)

Trainer names/classes (pret decompilation), long ability effect texts
(PokéAPI has no German `effect_entries`), Smogon set names
(data.pkmn.cc), user-generated content. Runtime-generated Nuzlocke feed
entries are written in the then-active language and do not retro-translate.
